This is one product with three surfaces: a store where people buy album covers, a credits system that's the business engine, and a studio where people spend credits to make the cover they bought their own.

The business model. A customer browses a curated gallery of professionally designed album covers, buys one, and immediately receives AI credits included with the purchase. They then go into the studio, select that cover, and use credits to alter it — change the mood, palette, typography, composition details — with generative AI. They can also buy more credits separately. Credits are the recurring revenue; the cover sale is the entry point. The studio must respect the cover they bought: an edit should make their cover better, not turn it into a different image.

What actually makes this special — build this as a first-class feature, not an afterthought. The generative pipeline needs built-in knowledge and a prompt corrector. This is the differentiator, so it gets its own module:

Genre/style knowledge base. A structured taxonomy of music genres and subgenres (hip-hop/trap, metal, lo-fi, jazz, synthwave, ambient, pop, EDM, indie rock, classical, soul, punk, etc.), each carrying the visual conventions of that genre — palette, texture, mood, typography, iconography, reference points from classic album art. This lives in code (typed data, versioned), because it's the controlled vocabulary the whole studio depends on.
Prompt corrector. The user types something vague — "make it moodier, more underground, less colorful." The corrector parses that intent, classifies what kind of change it is (color shift / mood / add element / style transfer / typography / composition), checks it against the knowledge base, and expands it into a technically-sound image prompt that is constrained to preserve the base composition. It assembles a final prompt from: the genre conventions + a base "keep-the-original-composition" constraint + the parsed user edit. If the user's request is unsupported, ambiguous, or would destroy the design, the corrector fails closed: it refuses, or asks a clarifying question rather than guessing and generating garbage. Never generate on a bad prompt. Never silently reinterpret "moodier" as "golden hour photo."
Constrained edits. The studio must keep the identity of the purchased cover. This means the generation path is image-conditioned (img2img with controlled strength, or region inpainting for targeted edits) rather than text-to-image from scratch. The customer owns a variation of what they bought, not a different picture.
Engineered guardrails — non-negotiable:

Credit ledger integrity. Credits are a transactional ledger, not a counter. Every grant (cover purchase, credit pack), every spend (generation), and every refund is an atomic, auditable record. Credit grants must come from verified payment webhooks, never from client code — a user must not be able to grant themselves credits by editing a request. Spends are recorded atomically and are rollback-safe on a failed generation. Build the ledger so it can answer "why does this user have these credits" at any time.
Margin math, in config. Define the cost per image generation and the price per credit as configured values with a documented calculation, so the margin per cover sale and per credit pack is explicit and I can retune it without touching logic. Make the cost of the included credits a visible line item in the cover's unit economics.
Fail closed everywhere. Unsafe, unsupported, or damaging generation requests refuse loudly. Payment, generation, and credit failures surface clearly to the user and never silently succeed. If a generation fails after charging, the credits are returned and the user is told.
Licensing is part of the product. Each cover has a license (non-exclusive commercial use with purchase is the default). The license terms display at checkout and are stored with the order. Downloads come with the license.
Stack. Next.js (App Router) + TypeScript on Replit. Supabase for Postgres and auth (or Clerk if you prefer that as the auth layer). Stripe for payments and webhooks. Supabase Storage (or S3) for cover assets. Replicate for image generation (Flux family: text-to-image for the base gallery generation, plus an img2img/inpainting model for the constrained studio edits). The prompt corrector is an LLM function with a typed schema, and it must call the genre knowledge base, not freeform improvise.

Build order — do it in this order and keep each phase working before moving on:

Catalog + cover detail pages + Stripe checkout that grants credits for a purchase.
The credit system: ledger, packs, purchase flow, spend API, refund safety.
The studio: pick an owned cover → see it → run a constrained edit that consumes credits.
The intelligence layer: genre knowledge base + prompt corrector + constraint engine, wired into the studio.
Account: owned covers, download, license, generation history.
Design bar. This is a creative-purchase product. It should not feel like a generic SaaS dashboard. The storefront and studio should look like a place that sells art: strong typography, dark premium aesthetic, the cover art is the hero. No stock-component feel, no default Replit/tailwind-boilerplate look. The studio's UI should make the barely-technical user feel they made a tasteful creative decision, not that they operated a diffusion model.

Scope you should NOT build. Don't build a marketplace where artists upload their own work — it's an in-house curated gallery for now. No user-uploaded reference images. No social features. No cover generation from a bare prompt (generation is for editing owned covers, plus the catalog generation tool I use). Don't spend effort on features outside the three surfaces above.

When you hit an ambiguity, make the decision that most preserves: (1) credit/ledger correctness, (2) the quality and identity of the art, (3) margin clarity. Choose in that order. Tell me the decisions you made and why, rather than asking me a long list of questions up front.
